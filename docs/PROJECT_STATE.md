## 1. What GoHa is

Private, account-scoped personal execution system. The chain is:

Life Area -> Goal -> Sub-goal -> Task / Habit -> Today -> Focus -> Complete -> Reflect

The governing rules live in `CLAUDE.md` and are not repeated here.

## 2. Stack

Next.js 16 App Router, React 19, TypeScript strict, Tailwind 4, pnpm.
Neon Postgres + Drizzle ORM/Kit. Better Auth (email/password). Zod at every
server boundary. Vitest + Playwright. Timezone default Asia/Manila.

## 5. Core entities

`user` -> `user_settings` (timezone, rhythm times, automation toggles)
`life_areas` -> `goals` (self-referencing `parent_goal_id`, max 2 levels)
-> `tasks` (self-referencing `parent_task_id` for subtasks)
`habits` -> `habit_schedules`, `habit_entries` (`entry_date DATE` + `created_at TIMESTAMPTZ`)
`focus_sessions` (optional `task_id`, `session_date DATE`, `note`)
`day_plans` -> `day_plan_allocations` -> `day_plan_items`
`planner_default_categories` (per user, no children)

Rule: date-bucketed concepts are `DATE` in the user's zone; audit stamps are
`TIMESTAMPTZ`. Never truncate UTC to get a local date. Helpers in `lib/date.ts`.

Route Handlers exist only where a Server Action cannot work: Better Auth,
push pairing, personal-token APIs, `/api/health`, and the internal worker
surface below.

## 7. Day Planner architecture

A CAPACITY tool, not a calendar. No hour grid, no start times.

Hybrid defaults model, and the boundary is the whole safety property:

- `planner_default_categories` is a TEMPLATE owned by the user.
- A `day_plans` row is one date and is independent once created.
- Seeding copies template -> day, in that direction only, and only into a day
  that has no categories yet.
- `saveAsDefaultsAction` is the ONLY writer of the template. No day-editing
  action may reach `replaceDefaultCategories`; enforced by
  `tests/planner-defaults-boundary.test.ts`.

Entries inside a category are either a linked to-do (`task_id`) or the user's
own text (`label`), never both, enforced by `day_plan_items_task_or_label`.
Reserved time is a category with minutes and no entries; it needs no row.

Actual time has two disjoint sources, and the disjointness is what makes the
sum safe rather than double counted:

- LINKED entries: derived from completed focus sessions. Never stored.
- FREEFORM entries: `day_plan_items.actual_minutes`, typed by the user.
  `day_plan_items_actual_manual_only` makes a linked row carrying one
  unstorable, so redundancy is impossible rather than merely discouraged.

`null` means "not recorded" and is distinct from a recorded `0`. Recording is
refused for a future local date, resolved server-side from the entry's own plan.
There is no second timer: Focus Mode is the only automatic tracker.

Suggestions are pull-based and ranked, never placed. A life-area match is a
score bonus (`AREA_MATCH_BONUS`), not a filter. There is no list of category
names that behave differently, and no auto-fill.

Actuals: `focusActualsForDate` groups completed focus sessions by task for the
date; `dayActuals` in `lib/planner.ts` maps task -> category via this day's
entries and adds the manual minutes of that category's freeform entries. Focus
on a to-do that is not in the plan, or with no to-do at all, is reported as
unassigned and never absorbed into a category.

The day summary shows four numbers: Allocated, Planned work, Tracked
(focus + manual) and Focused (focus alone). The two are kept apart on purpose:
focus time is a measurement, manual time is the user's own estimate, and folding
them into one figure called "Focused" would restate a guess as a measurement.

Committing writes only `scheduled_for` on real task rows, which is how a plan
reaches Today through the same derivation as everything else.

Key files: `lib/planner.ts`, `lib/validations/planner.ts`,
`db/schema/planner.ts`, `db/repositories/planner.ts`,
`app/(app)/planner/{page,actions}.ts`, `components/planner/planner-view.tsx`.

## 8. Focus architecture

`focus_sessions` holds at most one `in_progress` row per user, enforced by a
partial unique index. Duration is derived from timestamps minus `paused_seconds`
when the session ends.

Notes are autosaved while the session runs (`saveSessionNote`, scoped to
`in_progress` so a finished session can never be rewritten), flushed before the
finishing write so the two cannot race, and `finishFocusSession` treats
`undefined` as "leave the column alone" so an abandon sweep cannot erase them.
They are rendered in Recent sessions by `components/focus/focus-stats.tsx`.

Key files: `lib/focus.ts`, `lib/focus-reconcile.ts`, `db/repositories/focus.ts`,
`app/(app)/focus/actions.ts`, `components/focus/*`, `stores/focus-timer.ts`.

## 9. Automation boundary

GoHa owns identity, dates, calculations, dedupe and Sabbath. n8n is a worker
and a presenter, never a source of truth.

GoHa has NO scheduler: `vercel.json` has `"crons": []`. Jobs are materialized
lazily inside `POST /api/internal/automation/jobs/claim`, on the user's own
local date, at or after the scheduled time, with no backfill. If nothing polls,
that day's notification is never created.

Worker surface (bearer auth, fails closed when the secret is unset):

| Endpoint | Purpose |
|---|---|
| `POST .../jobs/claim` | materialize + lease; returns `jobs[]` and `pollAfterSeconds: 300` |
| `GET .../jobs/{id}` | payload + `fallbackNotification` |
| `POST .../jobs/{id}/complete` | `{ notification: { title, body, url } }` |
| `POST .../jobs/{id}/fail` | report failure |
| `POST .../jobs/{id}/review-draft` | weekly review write-back |

Notification contract: `title` <= 80 chars, `body` <= 240 chars, `url` must be
an in-app absolute path. Enforced by `validateWorkerNotification`
(`lib/automation/worker-notification.ts`), which returns 422 on a breach.

Morning Brief, Evening Summary and Smart Reminders all require BOTH Daily Rhythm
times to be set; with either unset no job is ever materialized. Smart reminders
sit between the two times (+2h / -2h) and produce four jittered slots.

## 10. Notification architecture

Standards-based Web Push with VAPID. `push_subscriptions` (per device, with
`device_label`), `push_deliveries` (per device per notification, with provider
status), `notification_log` (per notification). Stale subscriptions are disabled
rather than deleted. No third-party push SDK.

## 11. Known limitations

- Migration 0023 is not applied to any database.
- The QA database credential in `E2E_DATABASE_URL` is stale: the endpoint
  `ep-polished-hill-ao93n9cv` rejects `neondb_owner` with a password
  authentication failure, so `pnpm db:migrate:test` cannot run.
- A freeform planner entry cannot be committed to Today: it has no to-do to
  schedule, by design.
- A freeform entry's actual time is manual and is not verified against anything;
  it is the user's own statement of what happened.
- Focus notes are editable only while the session runs; after it ends they are
  read-only, which is the documented `in_progress` scope.
- The n8n Central Dispatcher polls on its own schedule; a host outage silently
  loses that window's notifications because materialization is pull-driven.
